# Sales-Lite Workflow Plan

Дата: 19.05.2026

## 1. Цель изменения

Клиент подтвердил, что CRM больше не должна вести операционку по технике, подрядчикам, броням и выездам. Назначение техники, контроль брони и выездов выполняются в 1С.

Новый целевой процесс CRM:

1. Не обработан.
2. В работе.
3. Квалифицированный / Не квалифицированный.

Текущий полный контур нужно сохранить как альтернативу на будущее, поэтому внедрение идет через профиль процесса, а не через физическое удаление моделей и модулей.

## 2. Профили процесса

`full`:

- текущий функциональный контур;
- `Lead -> Application -> Reservation -> Departure -> Completed/Unqualified`;
- доступны заявки, брони, выезды, завершение, техника и подрядчики;
- используется как legacy/full-ops альтернатива и регрессионный профиль.

`sales-lite`:

- новый целевой контур продаж;
- `Не обработан -> В работе -> Квалифицированный/Не квалифицированный`;
- CRM хранит лид, клиентский контекст, контакты и заполненные менеджером данные;
- техника, подрядчики, брони и выезды не показываются в CRM UI;
- операционная часть остается за 1С.

## 2.1 Подтвержденные решения от 19.05.2026

- `Квалифицированный` в `sales-lite` отображается через существующий terminal stage `completed`, без обязательного нового backend enum на первом этапе.
- `В работе` можно вести через текущую сущность `Application`, но переименовать ее в UI и добавить правила перехода в следующую стадию.
- Старые операционные данные и API должны быть доступны только в `full`-профиле.
- Категории/типы техники можно оставить как текстовые подсказки для потребности, но не как полноценные операционные справочники техники/единиц/подрядчиков.
- Формат потребности в `В работе` требует отдельного уточнения: одна текстовая потребность или несколько строк/позиций внутри обращения.

## 3. Этапы внедрения

### Этап 1. Обратимый UI-профиль

- Добавить frontend env-флаг `VITE_CRM_WORKFLOW_PROFILE=full|sales-lite`.
- Оставить `full` значением по умолчанию.
- В `sales-lite` скрыть primary-домен `Операции` и справочники техники/подрядчиков.
- В `sales-lite` убрать сохраненные представления про брони, выезды и активные брони.
- Нормализовать старые deep-link/localStorage состояния на доступный sales-route.
- Переименовать стадии канбана в sales-lite без изменения backend enum.

### Этап 2. Подтверждение доменной модели

- Зафиксировать, является ли `Квалифицированный` новым backend stage или отображением существующего `completed`.
- Зафиксировано: `Квалифицированный` в первом этапе отображается через существующий `completed`.
- Зафиксировано: `Application` можно оставить технической сущностью для стадии `В работе` и переименовать в UI.
- Зафиксировать, какие поля менеджер заполняет в `В работе`, а какие уходят в 1С.
- Обновить `PRODUCT.md`, `DOMAIN_MODEL.md`, `ARCHITECTURE.md`, `ROUTES_AND_VIEWS.md`, `NAVIGATION_MODEL.md`, `API_CONTRACTS_OVERVIEW.md`, `RBAC_AND_PERMISSIONS.md`, `QA_REQUIREMENTS.md` после ответов.

### Этап 3. Backend profile guard

- Добавить backend env `CRM_WORKFLOW_PROFILE=full|sales-lite`.
- В `sales-lite` закрыть или выключить операционные endpoints для броней, выездов, завершения и справочников единиц техники/подрядчиков.
- Оставить таблицы и модули для `full`, чтобы не ломать старый профиль и данные.
- Сохранить `/api/v1` границу и server-side RBAC.

### Этап 4. Новые переходы стадий

- Ввести profile-aware transition map.
- Для `sales-lite` разрешить только подтвержденные переходы нового процесса.
- Сохранить audit logging для переходов и исходов.
- Не запускать миграцию данных до решения, что делать с уже созданными бронями/выездами.

Статус реализации 19.05.2026:

- Backend `POST /api/v1/leads/:id/stage` читает `CRM_WORKFLOW_PROFILE`.
- В `full` сохранена карта `lead -> application -> reservation -> departure` с terminal outcomes через completion flow.
- В `sales-lite` разрешены `lead -> application`, `lead -> unqualified`, `application -> completed`, `application -> unqualified`.
- В `sales-lite` переход `application -> reservation` запрещен, а UI drag-and-drop не предлагает его.
- При `application -> completed/unqualified` текущая Application закрывается как terminal/inactive; отдельная Completion-сущность не создается в sales-lite.

Минимальные поля перед `application -> completed` пока не расширялись сверх уже существующих требований для `lead -> application`; точный набор остается открытым вопросом QA-Q-058.

### Этап 5. Тесты и выпуск

- Добавить QA-REQ для нового sales-lite процесса.
- Оставить full-path contract/integration regression, чтобы альтернативный режим не деградировал.
- Добавить frontend checks на отсутствие скрытых nav/routes в sales-lite.
- Выполнять минимум:
  - `npm --prefix app/backend run typecheck`
  - `npm --prefix app/backend run build`
  - `npm --prefix app/frontend run build`

## 4. Вопросы к владельцу продукта

1. Нужна ли в `В работе` множественная структура позиций, или достаточно одного текстового описания потребности?
2. Какие обязательные поля должны быть заполнены для перевода из `В работе` в `Квалифицированный`?
3. Какой API-ответ ожидается для отключенной операционки в `sales-lite`: `403`, `404` или `410`?
4. Нужно ли поддерживать `full` в CI постоянно, или достаточно периодического regression-gate перед релизами?

## 5. Риски

- В текущей модели нет отдельного stage `qualified`; подтверждено, что на первом этапе это UI-смысл существующего `completed`.
- Старые документы и тестовые требования закрепляют full lifecycle как инвариант.
- Простое скрытие UI не является безопасностью; backend guard нужен отдельным этапом.
- Старые сохраненные ссылки на `/reservations`, `/departures`, `/completion` должны мягко уходить в доступный sales-lite маршрут.
- Данные старого операционного контура нельзя удалять до решения по legacy/full профилю.
